# 물 입자는 어떻게 표현했나 — `yongbin_drive_test.py --water`

배관 안에 물을 채우고, 그 물을 **흐르게** 하고, 로봇이 그 흐름을 거슬러
주행하게 만든 방식을 정리한다. 용어부터 하나씩 푼다.

관련 소스: `yongbin_drive_test.py`
- 상수 — `WATER` 블록 (파일 상단, `SETTLE_SEC`~`STOP_X_WATER`)
- 생성 — `# ══ 물 (--water): 흐르는 PBD 파티클 + 재순환 ══`
- 흐름 — `recycle_particles()`, `path_dist_tangent()`

---

## 0. 한 줄 요약

물을 **작은 공 2,623개**로 쪼개서 관 안에 격자로 깔고, 매 프레임 그 공들끼리
서로 밀어내게 해서 물처럼 굴게 만든다. 화면에 보이는 매끈한 수면은 그 공들을
감싼 **껍데기 면**을 실시간으로 다시 구운 것이고, 흐름은 하류로 빠져나간 공을
상류에 다시 떨어뜨리는 **러닝머신** 방식으로 만든다.

## 1. 용어

### 파티클 유체 (particle fluid)

물을 "연속된 덩어리"가 아니라 **입자(파티클) 여러 개의 모임**으로 본다.
입자 하나가 물 분자는 아니고, **물 한 덩이(여기서는 지름 약 9.6mm)** 를
대표하는 계산 단위다. 입자끼리 너무 가까워지면 밀어내고, 중력에 끌려 내려가고,
벽에 부딪히면 튕긴다. 이 규칙만으로 출렁임·수면·튀김이 저절로 나온다.

### PBD (Position Based Dynamics, 위치 기반 동역학)

물리 계산을 **힘 → 가속도 → 속도 → 위치** 순으로 푸는 대신, **"위치를 직접
고쳐서 규칙을 만족시키는"** 방식이다.

> 예: 두 입자가 겹쳤다 → 힘을 계산해 밀어내는 대신, 두 입자의 좌표를 서로
> 반대로 조금씩 옮겨 안 겹치게 만든다. 그 다음 "옮긴 만큼"을 속도에 반영한다.

빠르고 잘 안 터진다(수치적으로 안정적). 대신 물리적으로 정확하지는 않다 —
**게임·시각화용 유체**라고 보면 된다. 정확한 유량·압력 계산은 못 한다.
Isaac Sim(PhysX)의 파티클 유체가 이 방식이고, 그래서 소스에 `PBD` 라는 말이
나온다(`AddPBDMaterialWater`).

🔑 **이 시연이 답하는 질문은 "로봇이 물속에서 굴러가는가" 지 "유량이 얼마인가"
가 아니다.** 유량·수두 계산이 필요하면 PBD 가 아니라 수리학 공식(매닝 등)을
써야 한다 — §7 참고.

### 파티클 시스템 / 파티클 세트

- **파티클 시스템**(`/World/ParticleSystem`) — 규칙을 담는 그릇. 입자 크기,
  충돌 간격, 최대 속도, 바람 같은 **전역 설정**이 여기 붙는다.
- **파티클 세트**(`/World/WaterParticles`) — 실제 입자들의 **위치·속도 목록**.
  하나의 시스템 아래 여러 세트를 둘 수 있다(물 / 모래 / …).

### PointInstancer (포인트 인스턴서)

USD 에서 **같은 모양을 좌표 목록만 바꿔 수천 개 찍는** 장치. 구(sphere) 하나를
프로토타입으로 두고 위치 배열만 갱신하면 입자 전체가 움직인다. 구를 2,623개
따로 만드는 것보다 훨씬 싸다. 소스에서 입자 좌표를 읽고 쓰는

```python
water_instancer.GetPositionsAttr().Get()   # 지금 위치 전부
water_instancer.GetVelocitiesAttr().Set()  # 속도 전부 덮어쓰기
```

가 바로 이것이다.

### 오프셋 4형제 — 이 시연에서 가장 많이 데인 값들

| 값 | 뜻 | 이 시연 |
|---|---|---|
| `particle_contact_offset` (PCO) | 입자끼리 **서로를 느끼기 시작하는 거리** | 8mm |
| `fluid_rest_offset` | 유체 입자가 **가만히 있을 때의 간격의 절반** ≈ 입자 반지름 | 4.8mm |
| `contact_offset` | 입자와 **강체**(로봇·관)가 서로를 느끼기 시작하는 거리 | 4mm |
| `rest_offset` | 입자와 강체가 **맞닿았다고 볼 거리** | 2.5mm |

관례상 `fluid_rest_offset ≈ 0.6 × PCO` 다(8 × 0.6 = 4.8 ✔). 입자 지름은
`2 × fluid_rest_offset = 9.6mm`, 초기 격자 간격은 9mm — 즉 **처음부터 살짝
눌린 상태**로 깔아서 빈틈 없이 채운다.

🚨 **`rest_offset` 을 안 주면 로봇이 물 위에 뜬다.** 기록된 함정이다. 강체용
   간격이 기본값으로 크게 잡히면 입자가 로봇을 계속 밀어내서, 물에 잠겨야 할
   로봇이 입자 매트리스 위에 올라앉는다.

### 등위면 (isosurface)

입자는 그냥 두면 **공 무더기**로 보인다. 물처럼 보이려면 그 공들을 감싸는
**하나의 매끈한 면**을 만들어야 한다. 공간에 격자를 깔고 "이 지점이 입자에
얼마나 가까운가"를 재서, 그 값이 일정한 곳들을 이어 만든 면이 **등위면**이다
(등고선의 3D 판이라고 보면 된다).

```python
particleUtils.add_physx_particle_isosurface(
    grid_spacing        = rest*1.5,   # 면을 뜨는 격자 간격 — 촘촘할수록 곱고 느리다
    surface_distance    = rest*1.6,   # "표면"으로 칠 거리 — 크면 뚱뚱해진다
    grid_smoothing_radius = rest*2.0, # 울퉁불퉁함을 뭉개는 반경
    num_mesh_smoothing_passes = 8)    # 다 만든 면을 몇 번 더 다림질하나
```

그래서 소스는 입자 자체를 **안 보이게** 한다 — 등위면이 대신 렌더된다.

```python
UsdGeom.Imageable(_winst_prim).MakeInvisible()
```

⚠ 등위면에는 메모리 누수 이슈가 알려져 있다(소스 주석). **짧은 시연 세션
전용**으로 쓰고, 몇 시간짜리 배치에는 켜지 말 것.

### PBD 재질 (`AddPBDMaterialWater`)

점성(viscosity)·표면장력(surface tension)·응집력(cohesion) 같은 **물다움**의
계수 묶음. 물 프리셋을 그대로 쓴다. `materialPurpose="physics"` 로 붙는다 —
**보이는 색과 물리 성질은 다른 재질**이다:

- 물리용: `/World/WaterPBD` (PBD 물 프리셋)
- 시각용: `/World/WaterVisual` (파랑 + 자체발광 `emissiveColor`, 불투명도 0.85)

시각 재질이 유난히 진하고 스스로 빛나는 이유가 주석에 있다 — **유리 배관 너머로
보이기 때문이다.** 반투명(0.45) 물을 반투명(0.25) 유리 뒤에 두면 거의 안 보인다.

### GPU dynamics / broadphase

파티클은 **GPU 물리 전용**이다. 그래서 물 모드는 켤 때 이렇게 바꾼다.

```python
_pc.enable_gpu_dynamics(True)
_pc.set_broadphase_type("GPU")
```

- **브로드페이즈** — "누가 누구와 부딪힐 수 있나"를 대충 먼저 추리는 단계.
  수천 개 입자를 전부 짝지어 검사하면 못 쓰므로 공간을 쪼개서 후보만 추린다.

🚨 **GPU 로 바뀌면서 따라오는 제약이 셋이다** (전부 실측으로 데인 것):

| 증상 | 원인 | 대처 |
|---|---|---|
| 로봇이 관을 **뚫고 자유낙하** | `contactOffset 0.0005` 가 GPU 접촉 생성 허용치보다 작아 접촉이 전부 소실 | 물 모드는 오프셋 설정을 건너뛰고 엔진 기본값(0.02) 사용 |
| 초기 관통 → 로봇 **사출(+316m)** | 실린더 프리미티브는 커스텀 지오메트리라 GPU 미지원 | 휠 충돌을 `convexHull` 로 교체 (에지 채터로 슬립은 조금 늘어남) |
| 바퀴가 안 돎 | GPU 는 `reset()` **뒤의** USD 드라이브 변경을 무시 | 목표 회전속도를 reset **전에** USD 에 미리 기록 |

## 2. 물을 어디에 채우나 — 부분 충전(개수로) 흐름

```python
W_LEVEL_Z = 0.020      # 수위 (관 중심에서 +20mm)
W_R_MAX   = 0.045      # 관 내반경 45mm
W_SPACING = 0.009      # 격자 간격 9mm
```

관 단면(내반경 45mm, 6,362mm²)을 **가득 채우지 않는다.** 바닥부터 z=+20mm
까지만 채워서 **77%** 만 물이고 위쪽은 공기다. 관이 꽉 찬 것이 아니라 물이
바닥을 따라 흐르는 상태 — 수리학에서 **개수로 흐름(open channel flow)** 이라
부르는 조건이고, 실제 배수관이 이렇다.

채우는 방법은 단순하다. 관 축을 따라 9mm 간격의 **3차원 격자**를 만들고,
그중 "관 안쪽이면서 수위 아래" 인 점에만 입자를 하나씩 놓는다.

```python
for x in ...:                       # 관 축 방향
    for y in ...:
        for z in ...:               # 수위(+20mm)까지만
            if y*y + z*z <= R²:     # 관 단면 안인가
                입자 추가
```

→ 직관 코스 기준 **2,623개**.

🔑 **로봇이 설 자리는 비워 둔다** (`abs(x - START_X) < 0.10` 건너뜀). 입자와
로봇을 같은 자리에 겹쳐 두고 시작하면, 물리 엔진이 그 겹침을 푸는 임펄스로
로봇이 튀어나간다. 비워 둔 자리는 정착(SETTLE) 6초 동안 물이 저절로 흘러들어
메워진다 — `SETTLE_SEC = 6.0` 이 그 시간이다.

### 곡관 코스(`--elbow --water`)는 좌표를 다르게 판정한다

직관은 "관 축이 x" 라서 `y² + z² ≤ R²` 한 줄로 끝난다. 그런데 코스가
`직선 → 90° 곡관 → 직선` 으로 꺾이면 그 식이 안 통한다. 그래서
`path_dist_tangent(x, y)` 가 **중심선까지의 거리**를 재 준다:

1. 점에서 직선 구간·원호 구간·출구 직선 구간 각각까지의 거리를 잰다
2. 그중 **가장 가까운 구간**을 그 점이 속한 구간으로 본다
3. 그 구간까지의 거리 `d` 와, 그 자리의 **접선 방향**(로봇이 나아갈 방향)을 돌려준다

그러면 `d² + z² ≤ R²` 로 굽은 관 안쪽인지 판정할 수 있다. 굽힘이 수평면(x-y)에
있어서 **수위 z 는 전 구간 동일**하다 — 이게 성립하도록 곡관을 눕혀 놓았다.

## 3. 물을 어떻게 흐르게 하나 — 두 가지 방식

### 직관: 전역 바람(wind)

```python
wind = Gf.Vec3f(FLOW_V, 0.0, 0.0)      # -X 방향으로 일정하게 민다
```

파티클 시스템에 **모든 입자를 한 방향으로 미는 힘**을 걸어 둔다. 간단하지만
**단방향뿐**이다.

### 곡관: 접선 방향으로 속도 끌어당기기

곡관에서는 물이 관을 따라 **돌아야** 하는데, 전역 바람은 늘 같은 방향이라
못 쓴다. 그래서 곡관 코스는 바람을 0 으로 두고 `recycle_particles()` 에서
**입자마다 직접** 속도를 손본다.

```python
d, tx, ty = path_dist_tangent(pts[:,0], pts[:,1])   # 그 자리의 접선
vels[:,0] += FLOW_BLEND * (-tx*spd - vels[:,0])     # 목표 속도로 조금씩 당김
vels[:,1] += FLOW_BLEND * (-ty*spd - vels[:,1])
```

읽는 법: `현재 속도 += 0.20 × (목표 속도 − 현재 속도)`. 한 번에 목표로 못
박지 않고 **20%씩 다가간다**(`FLOW_BLEND = 0.20`). 확 박으면 물이 물처럼
안 굴고 컨베이어 벨트처럼 뻣뻣해진다. 부호가 `-tx` 인 것은 **로봇 진행 방향의
반대** — 로봇이 물살을 거슬러 올라가는 정찰 임무 조건이기 때문이다.

## 4. 러닝머신 — `recycle_particles()`

입자를 계속 새로 만들면 수가 무한히 늘어난다. 그래서 **개수는 고정**하고,
하류로 빠져나간 입자를 **상류에 다시 떨어뜨린다.** 러닝머신 벨트와 같다.

재투입 대상(하나라도 걸리면 옮긴다):

| 조건 | 뜻 |
|---|---|
| `x < RECYCLE_OUT_X` | 하류 끝(관 입구)으로 빠져나갔다 |
| `off > 0.055` | **관벽을 뚫고 새어 나갔다** (내반경 45mm 보다 밖) |
| `y > 상류 끝 + 0.02` | 상류로 너무 올라갔다 |

옮길 때는 상류 지점에 **약간씩 흩어서**(`uniform`) 놓고, 수면보다 조금 위
(`W_LEVEL_Z ~ +15mm`)에서 아래로(`vz = -0.2`) 떨어뜨린다. 수면 아래에 바로
꽂아 넣으면 그 자리 입자와 겹쳐서 폭발적으로 튄다.

호출 주기가 중요하다:

```python
RECYCLE_EVERY = _steps(1.0 / 60.0)     # "시간" 기준 1/60초
```

🚨 **스텝 수로 고정하면 안 된다.** GUI(렌더 켬) 한 스텝은 물리 4 서브스텝이라
   headless 의 4배 시간이 흐른다. 스텝 수로 박으면 GUI 에서 강제 주기가 4배
   뜸해져 **유속이 55 → 44 mm/s 로 떨어진다**(실측). 그래서 `_steps()` 로
   시간을 스텝으로 환산해 쓴다.

## 5. 전체 흐름 한눈에

```
① 파티클 시스템 정의     크기·간격·최대속도·바람        (규칙 그릇)
        ↓
② 재질 두 벌 붙이기      물리=PBD 물 / 시각=진한 파랑    (성질과 겉모습은 별개)
        ↓
③ 격자로 좌표 2,623개    관 안 + 수위 아래 + 로봇 자리 제외
        ↓
④ PointInstancer 로 생성  위치·초기속도 배열을 한 번에
        ↓
⑤ 등위면 켜고 입자 숨김   매끈한 수면으로 렌더
        ↓
⑥ 매 1/60초 recycle()    접선 방향 유동 강제 + 이탈 입자 상류 재투입
```

## 6. 이 표현이 만들어 내는 부작용(의도된 것)

물이 있으면 로봇 조건도 같이 바뀐다.

```python
FRICTION = (0.30, 0.25) if WATER else (0.40, 0.35)   # 만관(정찰) / 배수(수리)
```

**젖은 관벽은 덜 미끄러지지 않는다** — 정지/운동 마찰을 낮춰 잡았다. 물 모드의
주행 판정은 이 낮은 마찰 위에서 나온 값이라, 마른 관(수리 임무) 결과와 직접
비교하면 안 된다.

또 물 모드는 앞서 말한 GPU 제약 때문에 **휠 충돌이 실린더가 아니라 convexHull**
이다. 다각형 근사라 모서리가 걸리는 **에지 채터**가 생겨 슬립률이 조금 높게
나온다 — 물 때문인지 근사 때문인지 구분해서 읽어야 한다.

## 7. 🚨 데모 유속 ≠ 설계 유속

```python
FLOW_V = -0.10        # 데모 기본값 0.10 m/s
```

v3 설계값은 **매닝 공식**(경사 S=1/100 기준)으로 구한 **0.86 m/s** 다. 8.6배
차이다. 그런데 유체 항력은 속도의 **제곱**에 비례하므로:

> 0.86 / 0.10 = 8.6배 → 항력은 **74배**

즉 **기본값으로 돌린 시연에는 설계 항력(2.3N)이 사실상 안 들어가 있다.**
임무 조건을 검증하려면 반드시 유속을 올려서 돌려야 한다.

```bash
PYTHONUNBUFFERED=1 isaac_python yongbin_drive_test.py --elbow --water --flow 0.86
```

- `--flow <m/s>` — 유속(항상 상류 방향으로 부호가 잡힌다)
- `--blend <0~1>` — 유동 강제의 세기(기본 0.20). 올리면 물이 뻣뻣해지고
  내리면 물살이 흐물흐물해진다

**매닝 공식**(Manning) — 개수로의 평균 유속을 관의 거칠기·물이 찬 단면 모양·
경사로 추정하는 수리학 경험식. PBD 는 이런 값을 못 내주므로, **설계값은
공식으로 정하고 시뮬레이터에는 그 값을 넣어 주는** 관계다.

## 8. 실행 요약

```bash
# 화면(WebRTC)으로 보기 — --headless 를 빼야 렌더가 돈다
PYTHONUNBUFFERED=1 isaac_python yongbin_drive_test.py --water
PYTHONUNBUFFERED=1 isaac_python yongbin_drive_test.py --elbow --water --flow 0.86

# 수치만 (빠름)
PYTHONUNBUFFERED=1 isaac_python yongbin_drive_test.py --water --headless
```

로그의 이 줄이 물 설정 확인용이다.

```
물: 입자 2,623개, 유속 0.1 m/s (경로 접선 상류→하류, 재순환),
    마찰 0.3/0.25 (만관), GPU dynamics ON
```

주행 중 진행 로그에는 `유속 +100mm/s` 처럼 **실측 유속**이 같이 찍힌다 —
설정값이 아니라 입자 속도의 **접선 성분 평균**, 즉 물이 실제로 그만큼 흐르고
있는지를 보는 값이다. 부호 `+` 는 로봇 진행의 반대(거슬러 올라가는 중)라는 뜻.

⚠ 이 실측 유속 표시는 **`--elbow` 일 때만** 나온다. 직관 코스는 흐름을 전역
바람이 맡아서 `recycle_particles()` 가 유속을 재지 않기 때문이다.
