배관 + `robot_from_bot_welder_art_v2.usda` 조합으로 `src/son/repair_demo.py` 와
같은 일을 한다 — 주행 → 결함 접근 → 용접 → 판정.


🔑 **의존 방향이 뒤집혔다 (2026-08-06).** 원래 `course.py` 는 CATIA 메시를
역산한 기술(記述)이었다. 지금은 `course._SEGS` 가 정본이고 배관을

생성기는 매번 **연속성**(구간 이음매 틈 <0.01mm, 접선 꺾임 <0.1°)과

`doubleSided=0` 이라 관 안에서 아무것도 안 보이고 — 물리는 멀쩡한데 카메라

## 🚨 알아야 할 세 가지

### 1. 로봇이 출고 상태로는 이 배관을 못 지난다

벨로우즈 D6 4개의 스윙 리밋이 **±20°** 인데, R100 굽힘은 본체 중심간 124mm 에
대해 약 71° 를 요구한다. ±20° 로는 관절 4개가 전부 리밋에 붙어도 본체 사이
꺾임이 25° 밖에 안 나와 **첫 굽힘 입구 s≈388mm 에서 멈춘다.**

| 리밋 | 결과 |
|---|---|
| ±20° (출고값) | ❌ s=379mm 정지 |
| ±22 / ±23 / ±24° | ❌ 정지 |
| **±25°** | ✅ 완주 (임계) |
| **±30°** (기본) | ✅ 완주 41초 |
| ±40° | ✅ 완주 39초 |

데모는 `scene.relax_bellows()` 로 **스테이지에서만** ±30° 로 덮어쓴다.
usda 원본은 안 건드린다. `--flex 20` 으로 출고 상태를 재현할 수 있다.

→ 실기에 반영하려면 **벨로우즈 관절 설계를 바꿔야 한다.**

### 2. 정지만으로는 용접 정렬이 안 된다

휠은 강성 0 · 감쇠 0.012 N·m·s/rad 인 순수 속도 드라이브라 정지 토크가 거의
없다. 굽힘에서 접힌 벨로우즈의 복원력에 밀려 **2~4mm 이완**하는데 정렬 허용치는
1.5mm 다. `hold_station()` 이 오차에 비례한 속도를 계속 주되 데드밴드 밖에서는
**최소 명령 25 deg/s 를 깐다** — 그 밑으로는 토크가 안 나와 로봇이 꿈쩍도 않는다.

### 3. 토치가 관벽에 못 닿는다

팁 끝 반경 = 33(링) + 8(팁 원뿔) + 0~5(신장) = **41~46mm**, 관 내벽 50mm.
최소 간극 **4mm** 로 설계 용접 간극 2mm 에 못 미친다. 로봇 설계값이라 그대로
두고 로그에 실측만 남긴다(실측 간극 3.40mm — 로봇이 결함 쪽으로 살짝 편심).

## 검증이 자기충족이 아님

정렬 오차를 관벽 좌표에서 재서 1.5mm 안일 때만 결함을 없앤다. 비드는 성공·실패
무관하게 **토치가 실제로 있던 자리**에 생긴다.

`--no-creep` 이 실패하지 않으면 판정이 죽은 것이다 (아래 「대조군 3종」).

## 카메라 검출

전방 카메라 1대(어안 140°, 640x360)가 세 가지를 한다 — 찾기 / 겨누기 / 확인.
**정답 좌표는 점수 매기기에만 쓴다.**

```
[검출] 후보 기각 — 크기 ø169mm (허용 8~60)  (면적 44,065px, 사거리 187mm)
[검출] 벽면 구멍 후보 — 면적 2,268px → s=1599.4mm 시계각 179.3°  (로봇 s=1481mm)
[검출] ✅ 확정 — 일치 2회 → 목표 s=1599.5mm 시계각 179.3°
       검출 오차 축 -0.50mm / 시계 -0.68° (= 원주 -0.60mm)
```

### 🚨 굽힘에서 "관 저 끝"이 가짜 구멍으로 잡힌다

`repair_demo` 의 "화면 중앙에 걸리는 라벨은 관 저 끝" 필터는 **직관 전제**라,
굽은 관에서는 터널 끝이 중앙을 벗어나 그냥 통과한다. 실측으로 44,085px(화면의
19%) 짜리 가짜가 확정돼 로봇이 굽힘 한가운데로 용접하러 갔다.

**크기로 가른다** — 광선이 벽에 닿는 거리를 알면 화소 반지름에서 실제 지름이
나온다: `지름 = 2·r_eq_px·거리/f_px`. 가짜는 ø169~175mm 로 걸러지고 진짜는
ø28 근처다. 결함 위치를 전혀 안 쓰는 판별식이다.

### 🚨 찾을 때는 RGB. 확인할 때는 어느 한쪽도 못 믿는다

관통 구멍의 깊이는 inf 라 **찾기**는 RGB 여야 한다. 하지만 **검증**에서는 RGB 와
Depth 가 서로 다른 조건에서 실패한다 — 실측 두 건이 정반대였다:

| 조건 | RGB 구멍 검출 | Depth 프로파일 |
|---|---|---|
| `--no-weld` (불투명, 결함 그대로) | "구멍 없음" ❌ 놓침 | "파임 +3.69mm (447px)" ✅ |
| `--glass` (수리 실패) | "구멍 있음 4,509px" ✅ | "메워짐 −1.66mm" ❌ 놓침 |

RGB 가 놓치는 것은 결함이 화면 아래 가장자리라 관 저 끝의 큰 암부와 이어져
중앙 원판 필터가 그 라벨을 통째로 제외하기 때문이고, Depth 가 놓치는 것은
**비드 조각이 그 자리 벽을 다시 채우기** 때문이다.

→ **비대칭 규칙**을 쓴다. "구멍이 보인다" 는 결정적이지만 "안 보인다" 는 아니다:

```
① 예상 자리에 구멍이 보이면  → 미수리 (확정)
② 아니면 Depth 판정을 따른다
③ Depth 도 없으면 비드 유무로 본다
```

### 🚨 --glass 는 검출 정확도를 6배 떨어뜨린다

| | 검출 오차(축) | 정렬 오차 | 수리 |
|---|---|---|---|
| 불투명 | −0.4mm | 0.79mm | ✅ 성공 |
| `--glass` | **−2.3mm** | **2.55mm** | ❌ 실패 (허용 1.5mm) |

관이 반투명해지면 조명이 벽에서 반사돼 돌아오지 않아 대비가 죽는다. 검출 자체는
살아남지만(기울기 0.011 로 확정) 정확도가 허용치를 넘긴다.
**밖에서 들여다보며 용접까지 보려면 `--glass --no-vision`** 으로 정답 좌표를
겨누게 할 것.

물리에는 영향이 없다 — 굽힘 3곳의 주행 수치가 불투명 실행과 소수점까지 같다.

### 대조군 4종

```bash
isaac_python zigzag_demo.py --headless                        # 0.70mm  ✅ 수리
isaac_python zigzag_demo.py --headless --no-creep             # 11.87mm ❌ 실패
isaac_python zigzag_demo.py --headless --no-weld              # 아크 생략 → 미수리
isaac_python zigzag_demo.py --headless --glass                # 2.55mm  ❌ 실패
```

| 조건 | 정렬 오차 | 물리 실제 | 카메라가 본 것 | 검증 판정 |
|---|---|---|---|---|
| 기본 | 0.70mm | ✅ 수리 | 구멍 없음 / Depth 메워짐 | ✅ 일치 |
| `--no-creep` | 11.87mm | ❌ 실패 | 구멍 없음 / Depth 메워짐 | 🚨 불일치 |
| `--no-weld` | (생략) | 미수리 | 구멍 없음 / Depth 파임 | ✅ 일치 |
| `--glass` | 2.55mm | ❌ 실패 | **구멍 있음** / Depth 메워짐 | ✅ 일치 |

**정렬 판정은 4건 모두 물리 실제와 맞았다** — 자기충족 검증이 아니다.

`--no-creep` 에서 검증층만 불일치를 낸다. **검출기 잘못이 아니라 시각 모델의
한계다** — 비드 STL 이 44×47mm 벽 조각이라 어디에 놓이든 그 자리 벽을 메운
것처럼 보이고, 11.87mm 어긋나도 ø28 구멍이 조각 안에 들어가 RGB·Depth 둘 다
가려진다. 실기에서는 비드가 토치 자리에만 쌓이므로 안 생긴다.

> ⚠ 위 표의 "검증 판정" 열은 비대칭 규칙을 적용한 결과지만, **규칙을 바꾼 뒤
> `--no-weld`·`--no-creep` 를 다시 돌리지는 않았다.** 각 행의 "카메라가 본 것"
> 은 실측이고 규칙이 결정적이라 뒤집힐 여지는 없으나, 회귀 확인이 필요하면
> 세 조건을 다시 돌릴 것.

### 🚨 원인은 코스 연장이 아니라 **벨로우즈가 리밋에 붙어 있는 시간**이다

기본값(`--flex 30`)으로 전체 주행하면 두 번 다 죽었다. 증상은 아무 조짐 없이
**전 링크 transform 이 한꺼번에 무효**가 되고 `Illegal BroadPhaseUpdateData`
→ SIGSEGV. 그런데 **죽은 위치도 시각도 매번 다르다.**

| 실행 | 코스 | flex | 결과 | 죽은 지점 |
|---|---|---|---|---|
| A | hook 1.77m | 30 | ✅ 완주 41.0초 | — |
| B | long 5.05m | 30 | ❌ t=46.5초 | s≈1,826mm **직선** |
| C | long 5.05m | 30 | ❌ t=109.5초 | s≈4,374mm **곡선** |
| D | long 5.05m | 40 | ✅ 완주 117.8초 | — |

**같은 위치**면 기하 결함, **같은 시각**이면 누적 열화인데 둘 다 아니다.
스텝당 확률적 사건이다.

무엇에 비례하는지는 로그 통계가 말해 준다 — **관절이 리밋에 붙어 있는 표본 수**다:

| 실행 | 리밋 도달 표본 | 총 표본 | 비율 | 결과 |
|---|---|---|---|---|
| A hook/30 | 18 (>30°) | 38 | 47% | ✅ |
| C long/30 | 40 (>30°) | 107 | 37% | ❌ |
| D long/40 | 13 (>40°) | 116 | 11% | ✅ |

**비율이 아니라 누적 횟수와 맞는다** — 18·13회는 살고 40회는 죽었다.
굽힘에서 관절이 리밋에 눌려 있는 동안 큰 구속 반력이 생기고, 그 노출이 쌓이면
솔버가 터진다. 코스가 길어지면 **같은 상태로 더 오래 달릴 뿐**이다.

**그러므로 hook 이 완주하는 이유는 "안정해서" 가 아니라 "터지기 전에 끝나서"** 다.
hook 은 41.0초(약 9,840스텝)에 끝나는데 long 의 가장 이른 크래시가 46.5초다 —
**hook 은 41초 이후를 한 번도 시험한 적이 없다.**

### 이건 관 문제가 아니라 로봇 설계 문제다

위 「1. 로봇이 출고 상태로는 이 배관을 못 지난다」의 연장선이다. ±30° 는
"통과하는 최소값"이지 여유 있는 값이 아니었다 — 주행 표본의 **37~47% 동안
관절이 리밋에 붙어 있다.** 1.77m 는 그 상태로 버텨지고 5m 는 안 버텨진다.

| 리밋 | hook 1.77m | long 5.05m |
|---|---|---|
| ±20° (출고값) | ❌ s=379mm 정지 | ❌ |
| ±25° | ✅ 완주 (임계) | 미확인 |
| **±30° (기본)** | ✅ 완주 41초 | **❌ NaN** |
| **±40°** | ✅ | **✅ 완주 117.8초** |

→ 기본값을 40 으로 올리지 **않았다.** 이 숫자는 실기 벨로우즈 설계 요구사항
이기도 해서, 조용히 올리면 "±30° 면 된다" 는 잘못된 근거가 남는다.
long 코스를 돌릴 때 `--flex 40` 을 명시할 것.

**미확인** — 표본이 4회뿐이다. `--flex 35` 가 되는지, hook 을 40초 넘게
돌리면 같은 증상이 나오는지(직접 대조)는 아직 안 봤다. hook 을 `SPEED_MPS=0.015`
로 늦춰 시간을 맞추려 한 시도는 **로봇이 첫 굽힘에서 주저앉아**(s=357mm) 실패했다
— 저속에서는 굽힘을 넘을 토크가 안 난다. 이건 `repair_demo` 의 `SpeedGovernor`
를 이식하면 같이 풀린다.

## 물 채우기 현황 (`water_demo.py`)

로봇을 다 덜어내고 물만 남긴 단독 확인용이다. 계획·수치는 `TODO_WATER.md`.

```bash
ISAAC_STREAM=0 isaac_python water_demo.py --headless --s1 1.0 --steps 1200
```

| | 실측 (2026-08-06) |
|---|---|
| 채움 구간 | s 0~1,000mm (앞 1m) |
| 입자 | 4,812개 (충수 50%, 격자 9mm) |
| 물리 속도 | 74~76 step/s = **실시간의 0.31배** (240Hz 기준) |
| 관 밖 입자 | **0개** — 끝 마개·contactOffset 20mm 가 듣는다 |
| 수면 | 씨딩 z+0mm → 5초 뒤 **z−17.7mm** 로 가라앉는다 |

**미확인 — 전 구간(5m)은 아직 안 돌렸다.** 앞 1m 가 4,812개니까 전 구간은
약 22,000개고, 위 0.31배가 그대로 비례하지 않는다(입자 상호작용은 선형이
아니다). 늘리기 전에 `ISO_PASSES=0` 으로 렌더 비용부터 떼고 볼 것.

🔑 **수면이 17.7mm 내려앉는 것은 정상이다.** 격자 9mm 로 뿌리지만 유체 rest
는 4.8mm 라 안정 상태에서 입자가 서로 당겨 조밀해진다. 즉 `WATER_FILL` 은
"몇 개를 어디에 뿌리나" 이지 "최종 수위" 가 아니다 — 수위를 맞추려면
`WATER_FILL` 을 올려 잡아야 한다.

## repair_demo.py 대비 미이식

- **`condition.detector` 관상태 판정** — 단절·비틀어짐(DISCONNECTED/MISALIGNMENT).
  결함 검출과는 다른 층이다.
- **물 입자(`--water`)** — PBD 파티클, 누수 가시화. `--fluid` 도 마찰만
  만관값으로 바꿀 뿐 해석적 유체력은 아직 안 건다.
  → **진행 중.** `water_demo.py`(로봇 없이 물만)가 먼저 나왔고 앞 1m 는
  검증됐다 — 아래 「물 채우기 현황」. `zigzag_demo.py` 에 얹는 것은 아직이다.
- **굽힘 안의 결함** — 결함/비드 STL 이 직관 전용(축 X 인 곧은 벽 조각)이라
  굽힘에 놓으면 벽에서 뜬다. 검출 단계에서 굽힘 후보를 기각한다.
